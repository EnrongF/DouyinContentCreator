## Episode Position

Episode 3 covers the MVP stage.

Episode 2 asks whether the product is worth building. Episode 3 asks what exactly should be built first and how to keep fast AI-assisted building from turning into drift.

```text
Idea: Is this worth building?
MVP: What exactly should we build first, and inside what boundaries?
```

## Episode Promise

Help the viewer understand that AI-era MVP risk is not only bad code. The deeper risk is losing product scope, architecture context, and shared decisions while shipping quickly.

One-sentence Chinese promise:

```text
AI 写得越快，越要先把边界和上下文写清楚。
```

## Exact Mental Upgrade

In the MVP stage, speed is guaranteed by AI tools. The founder's hard work is deciding the smallest focused product, the scope it deliberately excludes, and the architectural context every AI coding session must respect.

Compressed mental upgrade:

```text
AI 技术债，不只是代码烂，而是每次开工都重新猜一遍产品边界。
```

## Target Audience

- Technical founder using AI coding tools to build an MVP.
- Solo builder who keeps adding features because they are cheap to generate.
- Product founder who needs scope discipline before early users arrive.
- Startup operator trying to avoid a functional but incoherent product.

## Episode Spine

1. After validation, the next risk is not slowness; it is uncontrolled building.
2. MVP is still an evidence-gathering stage, not a full-product construction stage.
3. AI technical debt compounds when specs, architecture decisions, and context files are missing.
4. Cheap features create zero-friction scope creep.
5. Practical rule: write architecture context and scope boundaries before coding; every new feature needs user evidence.

## Retained Source Value

- MVP is the smallest focused iteration that puts a real solution in front of real users.
- MVP is still evidence-gathering about the solution.
- Genuine PMF evidence is return, payment, referral, or repeated use by a specific group.
- AI technical debt compounds when foundational decisions are not written down.
- Persistent context such as `CLAUDE.md` keeps AI from re-deriving decisions every session.
- Scope document defines what the product does, does not do, and what evidence justifies adding something new.
- AI coding sessions should execute product decisions already made, not become places to throw in new ones.

## Non-Cuttable Claims And Caveats

- MVP is still about evidence, not completeness.
- Some technical debt is acceptable at MVP, but AI technical debt can compound through context and architecture drift.
- The founder must define scope and architecture before AI coding accelerates the build.
- A feature should be added because user evidence justifies it, not because it is easy to build.
- Claude-specific artifacts are source examples, not universal law.

## Compression

### Core Claim

```text
AI 让代码变快以后，MVP 最需要先写清楚的不是功能清单，而是边界、架构和上下文。
```

### Compact Mental Model

```text
先写边界，再写代码。
```

Meaning:
- Define what the MVP does.
- Define what it deliberately does not do.
- Define what evidence would justify adding something.
- Keep architecture/context available to every AI coding session.
