核心论点

当研究任务足够宽、动态且高价值时，多智能体系统最有优势。

02
90.2%内部研究评测中，Claude Opus 4 主智能体加 Sonnet 4 子智能体，相比单智能体 Opus 4 的提升。
95%在 BrowseComp 分析中，token 用量、工具调用次数和模型选择解释了大部分性能差异。
80%仅 token 用量就解释了 80% 的差异，说明并行上下文和容量非常关键。
15x多智能体系统相对普通聊天交互的大致 token 用量。
适合不适合原因
许多独立研究方向可以并行推进。所有智能体都必须共享同一个上下文。子智能体通过分离关注点和上下文窗口来扩大搜索面。
信息量超过单一上下文窗口。步骤之间存在强依赖。并行搜索把大语料压缩成可用发现。
任务价值足以覆盖更高 token 成本。低价值任务只需要便宜直接的答案。普通 agent 约为聊天的 4x token，多智能体约为 15x。
为什么适合研究

研究是路径依赖的：下一步该做什么，取决于刚刚发现了什么。

03

开放式任务

复杂研究无法预先硬编码成固定路线，因为新的线索会不断改变正确路径。

自主多轮决策

模型需要在多次工具调用之间决定下一步，而不是执行一次性的线性流水线。

像人一样调查

好的研究会持续更新计划、追踪旁支联系，并在中间发现改变局面时调整方向。

原文推理设计含义
搜索是一种压缩：从巨大语料中提炼洞察。子智能体相当于并行压缩器，把最重要的信息交回主智能体。
独立上下文能降低路径依赖带来的干扰。每个子智能体可以沿着不同证据链、工具和提示词轨迹前进。
一组通用智能体可以突破单个智能体的限制。当模型能力足够强之后，协调机制就变成核心架构问题。

S&P 500 信息技术公司董事查询，说明为什么要做广度优先分解。

原文例子

文章提到一个任务：找出 S&P 500 信息技术板块公司所有董事。多智能体系统通过把任务拆给子智能体完成，而单智能体系统因为顺序搜索太慢而失败。

单智能体路线多智能体路线
一家公司接一家公司地搜索。按公司或信息源拆给多个子智能体。
一个上下文承载整场调查。多个上下文保留相互独立的搜索路径。
延迟随顺序查询线性增长。并行搜索压缩总耗时。
失败模式：太慢，无法完成任务广度。成功模式：给问题投入足够的并行 token 预算。
Token 扩展

原文的性能故事，本质上也是 token 预算故事。

05
主张原文证据含义
更有价值的工作需要更多 token。仅 token 用量就解释 BrowseComp 80% 的性能差异。多智能体通过独立上下文窗口扩展处理容量。
token 不是唯一因素。token 用量、工具调用数、模型选择合计解释 95% 差异。工具编排和模型选择仍是一阶决策。
更好的模型会放大 token 效率。升级到 Claude Sonnet 4 的收益大于在 Sonnet 3.7 上把 token 预算翻倍。架构和模型质量是复合关系，不是替代关系。
经济账必须成立。agent 约为聊天 4x token，多智能体系统约为 15x。只应在任务价值足够高时使用这种架构。

阶段关键细节
用户与系统用户问题创建 LeadResearcher 智能体。

子智能体每个子智能体执行 web_search，使用交错思考评估结果，再 complete_task。
循环主智能体综合结果，并决定继续研究还是退出循环。
CitationAgent处理文档和研究报告，定位引用来源，然后返回最终答案。
与 RAG 对比

文章把 Research 定义为动态搜索，而不是静态检索。

08
方法机制弱点Research 的替代方式
静态 RAG检索与输入问题相似的片段，再生成答案。可能错过需要根据中间发现调整方向的线索。多步搜索会随着调查推进改变方向。
子智能体压缩多个独立智能体用各自上下文探索不同方面。消耗更多 token，也带来协调复杂度。把压缩后的发现返回主智能体。
引用阶段独立智能体把结论映射回来源。需要额外处理一遍材料。在最终交付前提高归因质量。

搜索即压缩

系统让子智能体探索大语料，再把发现压缩为主智能体可用的信息。

路径依赖

研究会随着证据出现而变化，一次性流水线无法预先算出正确路线。

独立上下文

每个子智能体可以走不同轨迹，不污染主智能体的工作上下文。

早期失败模式

协调失败主要是行为问题，所以提示词是关键控制面。

问题原文例子修复方向
过度创建子智能体早期系统会为简单问题创建 50 个子智能体。按问题复杂度嵌入投入预算。
无休止搜索为不存在的来源持续搜索。教会系统充分性判断和停止条件。
沟通过噪智能体之间用过多更新互相干扰。约束通信和输出格式。
重复劳动模糊的“研究半导体短缺”会导致搜索重叠。给每个子智能体明确目标、来源、工具和边界。
工具选择错误如果上下文只在 Slack 中，搜索网页从一开始就注定失败。先检查可用工具，再把工具与用户意图匹配。

工具与 MCP 设计

Anthropic 像设计人机界面一样认真设计智能体工具界面。

11
原文细节为什么重要提示词/工具响应
如果信息只在 Slack 中，让智能体搜索网页从一开始就失败。错误工具不是低效，而是让任务不可能成功。根据用户意图选择工具，并优先使用专门工具。
MCP 服务器会暴露许多智能体没见过、描述质量不一的工具。可用工具面扩大后，工具歧义会放大。每个工具都要有清晰、互相区分的用途说明。
智能体行动前应检查可用工具。计划依赖于知道哪些信息面可以访问。让主智能体把工具映射到外部搜索、内部搜索或专用检索。
Claude 4 可以改进提示词和工具描述。团队构建了一个工具测试 agent，通过反复试用有缺陷工具来发现问题。让 agent 诊断失败并重写描述，这让后续完成时间减少 40%。
提示词原则

第 1 部分：观察行为、清晰分工、按复杂度投入。

12
#原则操作含义防止的失败
1像智能体一样思考用真实提示词和工具跑模拟，逐步观察行为。已有足够结果还继续搜索、查询过长、选错工具。
2教会编排器如何分工子任务需要目标、输出格式、工具/来源指导和边界。模糊分工导致重复劳动或遗漏。
3按复杂度扩展投入简单事实：1 个 agent、3-10 次调用；直接比较：2-4 个子智能体、每个 10-15 次；复杂研究：10 个以上子智能体。简单任务过度创建 agent，复杂任务投入不足。
4工具设计很关键工具用途必须互相区分，并编码选择启发式。需要专门信息源时使用了泛化或错误工具。
提示词原则

第 2 部分：改进工具、先宽后窄、引导思考、并行调用。

13
#原则原文具体细节
5让智能体自我改进Claude 4 可以诊断失败模式，并提出提示词或工具描述改进。
6先宽后窄智能体常默认生成很长很具体、结果很少的查询，所以提示词要求先用短而宽的搜索。
7引导思考过程主智能体使用 extended thinking 规划、选工具、评估复杂度和定义角色；子智能体在工具结果后使用 interleaved thinking。
8并行工具调用主智能体并行创建 3-5 个子智能体，子智能体并行使用 3+ 工具，复杂研究最多减少 90% 时间。

半导体短缺失败例子

当主智能体只给出“研究半导体短缺”这样的模糊任务时，一个子智能体研究 2021 年汽车芯片危机，另外两个重复研究 2025 年供应链。修复方式是更清晰地划分职责。

评估

评估重点不是固定路径，而是是否通过合理过程到达正确结果。

14
评分项judge 要回答的问题
事实准确性结论是否与来源一致？
引用准确性引用来源是否支持对应主张？
完整性用户要求的方面是否覆盖？
来源质量系统是否优先使用一手或权威来源？
工具效率是否用对工具，调用次数是否合理？

原文评估细节

  • 尽早从小样本开始；Anthropic 最初用了约 20 个真实使用问题。
  • 早期提示词修改可让成功率从 30% 到 80%，小评测能发现大变化。
  • 一个 LLM judge 调用，输出 0.0-1.0 分数和 pass/fail，反而比多个 judge 更一致。
  • 人工测试发现系统偏向 SEO 内容农场，而不是学术 PDF 或个人博客等更好来源。
  • 主智能体提示词的小改动会不可预测地改变子智能体行为，所以要评估协作模式。
生产可靠性

从原型到生产，主要难点是状态、追踪和部署。

15
挑战为什么对 agent 重要Anthropic 的应对
有状态执行agent 会跨许多工具调用运行，重启昂贵且影响体验。持久化执行、重试、检查点和失败恢复。
工具失败适应agent 可能在运行中遇到失败工具。把工具失败告诉模型，让它自适应，再结合确定性保护。
动态决策同一提示词可能走出不同工具路径和来源路径。完整生产追踪，用于诊断坏查询、差来源或工具失败。
隐私感知可观测性团队需要行为洞察，但不能读取用户对话内容。监控决策模式和交互结构。
部署agent 可能在代码、提示词或工具更新时仍在执行。使用 rainbow deployment，让新旧版本在渐进流量切换中并存。
同步瓶颈主智能体等待一组子智能体，子智能体无法实时协作。异步执行是未来方向，但会增加状态一致性和错误传播复杂度。

总结

Agent 质量来自架构、提示词、工具、评估和运维共同作用。

19

架构

当任务以广度和独立探索为主时，使用 orchestrator-worker。

提示词

编码投入预算、分工边界、工具选择启发式和停止行为。

工具

工具元数据是产品界面，差描述会显著增加失败和延迟。

评估

用灵活 rubric 评估结果，结合小评测、LLM judge 和人工测试。

可靠性

构建持久化执行、检查点、追踪、隐私感知可观测性和谨慎部署。

经济性

只有当任务价值足以支撑约 15x 聊天 token 用量时，才值得使用多智能体。
