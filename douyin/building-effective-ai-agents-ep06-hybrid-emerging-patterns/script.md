# Script

很多团队问的第一个问题是：
要不要做混合架构？
我的建议是，先把这个问题放慢一点。

在这份资料里，高级架构不是起点。
它是系统跑过之后，用证据长出来的结果。

起点仍然是单一、清楚、可观测的 Agent。
先证明一个窄任务真的值得自治。

再看哪里卡住：
请求太分散，就加路由；
领域太多，就加专门 Agent。

如果需要多个方向并行探索，才进入多智能体。
如果质量标准清楚，才加 evaluator。

所以混合架构不是新的最高层级。
它只是把 Single Agent、Workflow、多智能体，按问题组合起来。

一个常见组合，是动态路由。
简单请求走便宜路径，复杂请求才升级到更重的团队。

这很关键，因为多智能体大约会吃掉 10 到 15 倍 Token。
不是每个请求都应该付这个成本。

另一个组合，是保留单 Agent 的主路径。
只有边缘案例，才交给多智能体，或者人工接管。

动态生成 Agent 和点对点网络更激进。
资料把它们放在 emerging patterns：
好处是灵活，风险是更难预测。

真正的判断，不是架构名字。
而是控制要求、领域复杂度、资源、上线速度和业务价值。

所以第六集的结论是：
先做最小可行系统，
再让架构跟着运行证据演进。
