# Script

很多企业做 Agent，第一步就问错了。

他们先问：能不能做多智能体？

但真正该先问的是：这个业务问题，到底需不需要 Agent？

如果流程很清楚，规则也稳定，你需要的可能只是自动化，或者一个 Workflow。

Agent 真正适合的是另一类问题：路径不固定，需要调用工具，需要根据反馈调整，还要持续推进目标。

所以判断 Agent，不要先看技术名词，先看业务问题的特征。

第一类，流程清楚、风险较低。

比如固定格式的信息抽取、普通问答、标准报表。

这时不要急着上 Agent。用增强型 LLM，或者简单 Workflow，通常更便宜、更稳定。

第二类，步骤清楚，但需要控制。

比如审批、合规检查、内容从草稿到审核再发布。

这适合 Sequential Workflow。因为你知道每一步是什么，也需要留下过程。

第三类，目标清楚，但路径不清楚。

比如客户问题排查、市场研究、代码库理解、数据分析。

这时可以用 Single Agent。它自己计划、调用工具、观察结果，再继续调整。

但如果你要求每次第一次就百分百正确，单 Agent 就不够。

第四类，问题跨多个领域。

比如贷款风险评估，要同时看信用、市场、运营、合规。

这时 Multi-Agent 才有意义。不同 Agent 负责不同专业视角，最后再汇总。

但代价也很真实：成本更高、延迟更长、调试更难。

Anthropic 的材料提醒，复杂任务里，多 Agent 可以明显提升表现。

但它不是默认选项，而是复杂度真的值得时才用。

第五类，Agent 要碰真实业务系统。

比如 CRM、订单、支付、审批、内部数据库。

这时重点不再是 Agent 本身，而是 Harness。

你需要权限、日志、监控、评估、回滚、人工接管。

否则 Agent 不是生产力，而是一个会放大风险的自动执行器。

所以给业务团队的选择框架很简单：

先看流程是否固定。

再看风险是否可控。

再看是否跨多个专业领域。

最后看成本和治理能力。

一句话：不要为了显得先进而上多 Agent。

先用最小架构解决真实业务问题。

当问题复杂度上升，再逐步从 Workflow，到 Single Agent，到 Multi-Agent，到 Harnessed Agent System。

真正成熟的 Agent 项目，不是更复杂。

而是复杂度刚好够用。
